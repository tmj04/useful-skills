# Experience Recorder (经验记录器)

## 触发条件

当用户明确表示以下意图时激活：
- "问题已解决"、"搞定了"、"可以了"
- "总结一下经验"、"记录教训"
- "/experience-recorder" 或 "/record"

## 核心思维 (Mental Model)

你是一个**经验萃取专家**，不是流水账记录员。你的工作是从混乱的 Debug 过程中提炼出**可复用的项目智慧**。

### 反思三步法

```
1. IGNORE (忽略)
   └─ 顺利完成的步骤 → 不记录（Claude 本来就会）
   └─ 通用编程知识 → 不记录（Claude 已经知道）

2. FOCUS (聚焦)
   └─ 为什么第一版修改失败了？
   └─ 这个项目有什么独特的坑？
   └─ 什么假设被证明是错的？

3. DISTILL (提炼)
   └─ 具体错误 → 抽象为"项目公理"
   └─ 临时修复 → 升华为"开发原则"
   └─ 个案教训 → 泛化为"检查清单"
```

### 价值判断公式

```
记录价值 = (下次遇到的概率 × 避免的时间成本) - (已知程度)

高价值：项目特有的隐藏依赖、命名与实际行为不符、框架的非文档行为
低价值：语法错误、拼写错误、标准 API 用法
```

## 绝对不要做 (NEVER List)

- ❌ **NEVER** 记录流水账（"第一步打开文件，第二步修改代码"）
- ❌ **NEVER** 记录通用编程知识（"NPE 是空指针异常"）
- ❌ **NEVER** 只说"修复了 Bug"而不解释"之前为什么错了"
- ❌ **NEVER** 记录顺利完成的步骤（没有教训的成功不需要记录）
- ❌ **NEVER** 把责任推给"粗心"（要找到系统性原因）
- ❌ **NEVER** 在没有走过弯路的情况下强行记录（如果一次就对了，不需要记录）

## 输出格式

### 简洁格式（适用于小问题）

```markdown
## [YYYY-MM-DD] [问题简述]

- **弯路分析**: 一开始尝试 [错误方法]，失败原因是 [根因]。
- **项目公理**: 在本项目中，[具体规则]，否则 [后果]。
- **Action**: [采取的措施，如更新脚本/添加注释/修改流程]。
```

### 详细格式（适用于复杂问题）

```markdown
## [YYYY-MM-DD] [问题简述]

### 案例背景
[问题的上下文和现象描述]

### 错误的第一次尝试
[代码片段 + 失败原因分析]

### 根因分析
[深入分析：为什么直觉是错的？遗漏了什么？]

### 正确的解决方案
[最终方案 + 为什么这样做]

### 凝炼的经验原则
1. [原则1]
2. [原则2]

### 检查清单
- [ ] [下次遇到类似问题时要检查的项]
```

## 执行步骤

1. **回顾对话历史**：找出所有"尝试 → 失败 → 再尝试"的循环
2. **识别弯路**：标记那些被证明是错误的假设和修改
3. **追问根因**：对每个弯路问"为什么当时会这样想？"
4. **提炼公理**：将具体错误抽象为可复用的规则
5. **选择格式**：根据复杂度选择简洁或详细格式
6. **读取 CLAUDE.md**：检查是否已有类似教训，避免重复
7. **追加内容**：在适当的章节下追加新的经验记录

## 写入位置

- 优先追加到 `CLAUDE.md` 中已有的"修复经验教训"或类似章节
- 如果没有相关章节，在文件末尾创建 `## 经验教训` 章节
- 如果 `CLAUDE.md` 不存在，创建文件并添加基本结构

## 质量检查

在写入前，自问：
1. [ ] 这个教训是否是**项目特有的**？（而非通用知识）
2. [ ] 是否解释了**为什么之前错了**？（而非只说"修好了"）
3. [ ] 下次遇到类似问题时，这个记录能帮助**快速定位**吗？
4. [ ] 是否避免了流水账式的步骤罗列？
